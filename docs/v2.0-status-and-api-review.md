### The central judgement

What has been delivered so far is **renaming, which is the cosmetic half of API
clarity**. The structural half — how you construct an analysis, how you get
results out, how you set options — is untouched and is still the 1.x design.

There is no deprecation shim of any kind
(`grep -n "__getattr__\|DeprecationWarning\|deprecated" src/pystra/**/*.py`
returns nothing), so every 1.x call site breaks today with a bare
`AttributeError`. Releasing 2.0 in its current shape therefore spends the whole
breaking-change budget and buys the user snake_case spellings while leaving the
awkward parts in place. That is a poor trade, and the breaking-change budget
does not come round again for years.

**Recommendation: do not cut 2.0 until items A1–A6 below are done — they are
the entire reason to break the API.** With the module reorganization also
confirmed for 2.0 (see E), this is a larger release than a week's work, and the
sequencing in section E matters: mechanical renames and moves first, behind a
green test suite, then the structural design work in the final locations.

## A. API clarity — ranked by user pain

### A1. Constructor argument order is reversed between analysis families

Five different calling conventions for the same three concepts:

```python
Form               (stochastic_model, limit_state, analysis_options)      # form.py:44
CrudeMonteCarlo    (analysis_options, limit_state, stochastic_model, ...) # mc.py:45  — reversed
SensitivityAnalysis(limit_state, stochastic_model, analysis_options)      # sensitivity.py:59 — third order
SystemFORM         (system, stochastic_model, analysis_options, *, ...)   # system_form.py:60 — no limit_state
StrongMaximumTest  (form=None, *, stochastic_model, limit_state, ...)     # strong_maximum.py:86 — keyword-only
```

Because every parameter defaults to `None`, the mistake is silent at the call
site and surfaces much later as nonsense. Reproduced:

```python
mc = ra.CrudeMonteCarlo(model, limit_state)   # the Form idiom, applied positionally
# AttributeError: 'StochasticModel' object has no attribute 'get_transform'
# ...raised inside the constructor, naming neither the argument nor the mistake.
```

**Fix.** One signature for every analysis, keyword-only after the first two:

```python
Analysis(model, limit_state, *, options=None, **algorithm_specific)
```

Make `model` and `limit_state` required rather than `None`-defaulted, so a
missing argument fails at construction with a clear message.

### A2. Only FORM has a result object

`Form.run()` returns a frozen `FormResult` dataclass with well-chosen field
names (`failure_probability`, `design_point`, `alpha`, `converged`,
`iterations`). This is the best piece of API work in the branch.

It is also the only one. `results.py` defines `FormResult` and nothing else.
`Sorm.run()` returns `None` and defines **zero** `get_*` methods; its outputs
are mixedCase attributes that survived the rename pass:

```
sorm.betaHL, sorm.pf2_breitung, sorm.betag_breitung,
sorm.pf2_breitung_m, sorm.betag_breitung_m          # sorm.py:101-108
```

So the user learns one idiom for FORM and a different, worse one everywhere
else. Meanwhile the same number has three names on `Form` alone: `Form.Pf`
(mixedCase attribute), `Form.get_failure()`, and
`FormResult.failure_probability`.

**Fix.** `SORMResult`, `SimulationResult`, `SystemFORMResult`,
`SensitivityResult`, all frozen dataclasses on the `FormResult` pattern;
`run()` returns them. Then delete the duplicate accessors — the result object
is the contract, and the getters are the transition scaffolding.

**This is the single highest-value item in the release.**

### A3. `AnalysisOptions` is a Java-style bean with cryptic names

`AnalysisOptions.__init__` takes no arguments, so options can never be set in
one expression. Each setting is then reachable three ways — public attribute,
`get_x()`, `set_x()` — and the attribute and getter often disagree on the name:

| Attribute | Getter | Problem |
| --- | --- | --- |
| `stdv_sim` | `get_simulation_stdv()` | word order reversed |
| `target_cov` | `get_simulation_cov()` | unrelated name |
| `i_max` | `get_imax()` | underscore dropped |
| `Ro_method`, `Recorded_u`, `Recorded_x` | *(none)* | PascalCase, no getter |

The names themselves are opaque to anyone who has not read the source: `e1`,
`e2`, `ffdpara`, `ffdpara_thetag`, `flag_sens`, `diff_mode`, `transf_type`.
Worse, there are two parallel transform settings that do not agree on type:
`self.transf_type = 3` (a magic integer, `analysis.py:156`) and
`self.transform_type = None` (a string enum, `analysis.py:290`).

**Fix.** Per-algorithm frozen dataclasses (`FORMOptions`, `SimulationOptions`)
constructed with keyword arguments and readable names
(`e1` → `convergence_tolerance_limit_state`, `e2` → `convergence_tolerance_direction`,
`i_max` → `max_iterations`, `flag_sens` → `compute_sensitivities`). Retire
`transf_type` outright. Record every old→new option name in the migration guide.

### A4. Namespace: 123 public names, no `__all__`, and the flagship feature missing

`src/pystra/__init__.py` has no `__all__` and performs 17 wildcard imports, so
`dir(pystra)` returns 123 public names. Five of them are not PySTRA at all, and
a further 26 are internal submodules exposed as a side effect of the wildcards:

```
ra.np          -> numpy
ra.optimize    -> scipy.optimize
ra.OrderedDict -> collections
ra.normal      -> scipy.stats norm     # one keystroke from ra.Normal
ra.scipy_norm  -> scipy.stats norm
```

`ra.normal` versus `ra.Normal` is a live footgun, and `ra.form` (the module)
sits next to `ra.Form` (the class). At the same time **`ra.ActiveLearning` does
not exist** — the `active_learning` subpackage has a clean `__all__` of its own
but is never surfaced at the top level, so the headline new capability of 2.0 is
the one feature the user cannot reach from `import pystra`.

**Fix.** An explicit `__all__` curated to roughly 40 names; per-module `__all__`
so the wildcards stop leaking; export the active-learning entry points.

### A5. Analysis objects expose their own iteration internals

`dir(form)` returns about 40 public names, of which perhaps six are for users.
The rest are algorithm state (`G`, `Go`, `J`, `d`, `e1`, `e2`, `i`, `step`,
`gradient`), ten `compute_*` step methods, and `N_HYPH` — a console
separator width (`analysis.py:48`) that is public on every analysis class.

**Fix.** Underscore-prefix the algorithm internals and the console constant.
Once A2 lands, the result object is the public surface and this is safe.

### A6. Errors, and the absence of `__repr__`

- 25 `raise Exception(...)` sites in `src/pystra` (`model.py`, `fbc.py`, five
  `distributions/*.py`) for what are user-input errors. Users cannot catch them
  specifically. `system_form.py:70-95` and `ss.py:81` already raise precise
  `ValueError`s and show the pattern to follow; the package has no exception
  base class of its own today, so introducing one (`PystraError`, with
  `ValueError`/`TypeError` subclasses) and converting those 25 sites is the fix.
- `StochasticModel.get_variable(name)` (`model.py:143`) is a bare dict lookup, so
  a mistyped variable name raises a raw `KeyError`.
- Only two classes define `__repr__` — `Distribution`
  (`distributions/distribution.py:166`) and `CorrelationMatrix`
  (`correlation.py:45`). No analysis class and no `StochasticModel` does, so
  `repr(form)` is `<pystra.form.Form object at 0x75f8...>`. For a package used
  mainly in notebooks this is a real cost, and `FormResult`'s dataclass repr
  shows how much better it can be for free.

### A7. Acronym casing — SETTLED: `FORM` and `SORM`

PEP 8 settles this. From *Descriptive: Naming Styles*: *"When using acronyms in
CapWords, capitalize all the letters of the acronym. Thus HTTPServerError is
better than HttpServerError."* FORM and SORM are acronyms in exactly that sense,
so `Form` and `Sorm` become **`FORM`** and **`SORM`**.

This also makes the package self-consistent — `SystemFORM`, `DDO`, `LQI`,
`SWTP`, `FBCProcess` and `KOfNSystem` already follow the rule, and the
documentation prose has always written FORM and SORM.

Exact scope — **nine** existing classes change. Note this is more than a first
pass suggests: enumerating `dir(pystra)` finds only three, because (per A4) the
`active_learning` subpackage is not exported at top level. A sweep of all 121
classes across every submodule finds six more:

| Current | 2.0 | Acronym |
| --- | --- | --- |
| `Form` | `FORM` | First Order Reliability Method |
| `Sorm` | `SORM` | Second Order Reliability Method |
| `FormResult` | `FORMResult` | " |
| `PceSurrogate` | `PCESurrogate` | polynomial chaos expansion |
| `PceCandidate` | `PCECandidate` | " |
| `PceFitResult` | `PCEFitResult` | " |
| `PcKrigingSurrogate` | `PCKrigingSurrogate` | polynomial chaos Kriging |
| `PcKrigingFitResult` | `PCKrigingFitResult` | " |
| `FbrLearning` | `FBRLearning` | failed bootstrap replicates |

and the classes A2/A3 will add inherit the rule: `SORMResult`,
`SystemFORMResult`, `FORMOptions`, `SORMOptions`. Function and attribute names
are unaffected — PEP 8's rule is about CapWords, so `run_form`, `pc_kriging.py`
and `get_equivalent_beta` stay snake_case.

**The contributor policy actively blocked this and has been corrected.**
`CONTRIBUTING.md` previously read "Do not mechanically recase class names during
the migration; existing `Form` and `Sorm` also retain their names" — the codified
form of commit `0905fc5`. Any contributor or agent following it would have
reverted the rename. It now states the PEP 8 rule as a single uniform
requirement, with `ScipyDist` as the one deliberate exception; the GEV names
were settled afterwards (section E).

Blast radius, measured: 27 occurrences in `src`, 24 in `tests`, 89 in
`docs/source` for `Form`; 1/13/34 for `Sorm`; 19/0/13 for `FormResult` — about
190 sites for those three, plus the six active-learning classes, entirely
mechanical and fully gated by the 719-test suite plus the zero-warning docs
build.

Not changing: `ScipyDist`. The GEV classes follow the family rule (section E).
An earlier version of this document called `GEVmax`/`GEVmin` a "conventional
statistical spelling". There is no such convention — it is simply the existing
name — and that wording has been withdrawn here and in the contributor guide.

## B. Documentation UX

The prior [documentation UX review](documentation-ux-review.md)'s P0 and P1
items are genuinely implemented — version/install lead, homepage rewrite,
practical user guide, direct API links, unified contributor docs. Navigation has
no orphaned or duplicated pages, and the first-run notebook
(`ex_first_analysis.ipynb`) is correct, copy-pasteable and uses v2.0 spellings
throughout. The guide / tutorial / theory / API split is real and works.

Remaining gaps, in priority order:

**B1. The migration guide is incomplete, and silently so.**
`docs/source/migrating.rst` never mentions five class renames that are recorded
in `naming-map.json`:

```
TypeIlargestValue    -> Type1LargestValue
TypeIIlargestValue   -> Type2LargestValue
TypeIsmallestValue   -> Type1SmallestValue
TypeIIIsmallestValue -> Type3SmallestValue
KofNSystem           -> KOfNSystem
```

A 1.x user hits a bare `ImportError` with no guidance in the readable page —
the information exists only inside a downloadable JSON file. **Generate the
migration table from `naming-map.json` at build time** so the guide cannot drift
from the maps again.

*Update, 10 September 2026:* `migrating.rst` now carries a readable
renamed-classes table. Its four extreme-value rows are superseded by the family
names decided in section E and have moved to the scheduled-renames table.

**B2. Add migration signposts, not aliases.** The "clean break, no permanent
aliases" decision is right, but it is currently implemented as *zero*
transitional help. A module-level `__getattr__` that raises a helpful error —
"`addVariable` was renamed `add_variable` in PySTRA 2.0; see the migration
guide" — is about 30 lines generated from the JSON maps already in the repo. It
is a signpost, not an alias, and it costs nothing to remove in 3.0.

With the module reorganization now in 2.0 (section E), this is no longer just
the cheapest large UX win — it is **mandatory**, and it must cover moved import
paths as well as renamed attributes. A package-level `__getattr__` cannot catch
`import pystra.form` once that file moves, because `ModuleNotFoundError` is
raised before any hook runs; leave a thin stub module at each old path whose
body raises a helpful `ImportError` instead.

**B3. The package's own quick start teaches the superseded idiom.**
`src/pystra/__init__.py:20-32` shows `form.run(); form.get_beta()` — the
mutate-then-getter pattern — despite `run()` already returning a `FormResult`.
This docstring, the README and `get_started` are the first API most users read,
and they should teach the result contract:

```python
result = ra.FORM(model, limit_state).run()
print(f"beta = {result.beta:.3f}, pf = {result.failure_probability:.3e}")
```

**B4. `show_results()` output.** The first output a new user sees prints
`Reliability index beta:    3.5355339059331268` — sixteen digits — and the
"Number of calls to the limit-state function" line breaks the column alignment
of the block above it. Format to a sensible precision and align the labels.

**B5. Smaller items.**
- `SensitivityAnalysis` has theory, API and a tutorial but no practical guide
  page in `guides/`, and is missing from the `api/reliability.rst` entry table.
- `src/pystra/cholesky_sensitivity.py` is public and used but appears in no
  `api/*.rst`.
- `docs/source/theory/active_learning.rst` has a literally duplicated title.
- `active_learning.rst`, `copulas.rst` and `system.rst` each mix how-to, theory
  and internal validation notes on one page.
- `docs/source/notebooks/ex_openseespy.ipynb` is untracked, in no toctree, and
  still uses 1.x camelCase (`addVariable`, `showDetailedOutput`). Track and fix
  it, or delete it — it is the only stale-API artefact left in the tree.

## E. Decisions and stages

The [migration plan](v2.0-migration-plan.md) is the document of record. The
decisions below are recorded there (§4, §5, §9 and §10), and its §7 now carries
the full staged sequence with status. This section summarises it and no longer
keeps its own step numbering.

The current goal — stages 2 to 4, stopping when the branch is ready to be tagged
`2.0.0a1` — is set out at the top of the plan.

### Decisions taken, 10 September 2026

1. **Acronym casing follows PEP 8.** The nine classes in A7 become `FORM`,
   `SORM`, `FORMResult`, `PCESurrogate`, `PCECandidate`, `PCEFitResult`,
   `PCKrigingSurrogate`, `PCKrigingFitResult` and `FBRLearning`.
2. **The module reorganization ships in 2.0.** This corrects the
   recommendation this document originally made. `pystra.form`, `pystra.mc`
   and the other top-level modules are importable paths, so moving them *is* a
   breaking change — 28 direct submodule imports exist in this repo's own tests
   and notebooks alone. A 2.1 that moved them would break semantic versioning,
   so the real choice was never "2.0 or 2.1" but **"2.0 or 3.0"**.
3. **Active learning is a first-tier method package** at
   `pystra.active_learning` — a peer of `reliability/`, not nested under it or
   under `calibration/`. It may import `reliability/`, never the reverse. Its
   entry points are exported from `pystra` like `FORM`, which closes the A4 gap.
4. **Extreme-value distributions are named by family, not by type numeral.**
   Roman numerals are the literature's convention — Type I (Gumbel), Type II
   (Fréchet), Type III (Weibull) — and 1.x used them. The v2 pass's Arabic
   `Type1LargestValue` matched neither the literature nor 1.x, and is
   superseded:

   | 1.x | Development branch now | 2.0 | Basis |
   | --- | --- | --- | --- |
   | `TypeIlargestValue` | `Type1LargestValue` | `Gumbel` | Bit-identical to the existing `Gumbel` (pdf, cdf, ppf); removed |
   | `TypeIIIsmallestValue` | `Type3SmallestValue` | `Weibull` | Bit-identical to the existing `Weibull`, including the shift; removed |
   | `TypeIIlargestValue` | `Type2LargestValue` | `Frechet` | Fréchet (SciPy `invweibull`); ASCII identifier |
   | `TypeIsmallestValue` | `Type1SmallestValue` | `GumbelMin` | Reflected Gumbel (SciPy `gumbel_l`) |

   Rule: the bare family name is the conventional flavour — maxima for Gumbel
   and Fréchet, minima for Weibull — and the opposite flavour takes a suffix.
   Keeping `Gumbel` and `Weibull`, both in v1.6.0, as the surviving names means
   no 1.x user of those two classes breaks.
5. **`LimitState` stays in `model.py`, beside `StochasticModel`.** Together
   they define the reliability problem — the uncertainty model and the
   performance function — so they belong in one module. The plan's original
   split into `limit_state.py` was aimed at the evaluation state `LimitState`
   carries (each evaluation stores the model, options and point on it), and
   moving the file would not have fixed that. Stage 4 does: evaluation moves
   into the analysis run and `LimitState` becomes pure specification.

### Settled later on 10 September 2026

- **GEV names:** `GEV` for maxima, with `GEVmax` kept as a permanent alias at
  the maintainer's request (the one deliberate alias in 2.0); `GEVMin` for
  minima, renamed from `GEVmin` with no alias.
- **Python floor:** 3.12. SPEC 0 dropped 3.11 in Q4 2025 and drops 3.12 in
  Q4 2026; NumPy 2.5 already requires 3.12; OpenSeesPy 3.8 needs only 3.10.
- **`cholesky_sensitivity`:** private, in `_numerics/`. A private module can be
  made public again without breaking anyone; the reverse cannot.

The order puts mechanical work first. Renames and moves are verifiable by a
cheap, strong gate — the suite stays green and the docs build without warnings
— so doing them before the structural work means new constructors, results and
options are written once, in their final location, and pure-move commits stay
separate from content commits in history.

**Signposts are mandatory**, because users face renamed classes and moved
import paths in one release. A package-level `__getattr__` cannot rescue
`import pystra.form` once the file moves — `ModuleNotFoundError` is raised
before any hook runs — so each of the 13 moved 1.x top-level modules keeps a
stub that raises a helpful `ImportError`, and renamed classes and functions get
`__getattr__` signposts generated from the naming maps. Both are removed in 3.0.

### Stage 2 — migration tooling

*Applied on 10 September 2026; kept for reference.*

**Do not do the class renames with a blind search-and-replace.** The migration
tooling hardcodes the old spellings in four places, and they do not all mean
the same thing:

| File | Occurrences | Action |
| --- | --- | --- |
| `scripts/api_inventory.py:152` | 1 | Hardcoded `"pystra.form.Form.run"` in the calibration-structure check. Must be updated by hand or CI fails with the misleading "Calibration structure inventory differs from current source". |
| `docs/migration/calibration-structure-map.json` | 8 | Regenerate. |
| `docs/migration/api-migration.json` | 80 | 40 entries carry `Form`/`Sorm` in **both** the `old` and `current` fields with `"status": "unchanged"` (the field is `current`, not `new`). Each flips to `"status": "renamed"` with a new `current` — regenerate via the script, do not sed. |
| `docs/migration/api-baseline.json` | 42 lines / 44 occurrences | This is the **1.x baseline**. It records where the migration came *from* and must keep the old spellings. Leave it alone. |

`naming-map.json` also changes: its four extreme-value entries now map to the
family names. `python scripts/api_inventory.py --check-names --check-migration`
passes today (verified), so it is a genuine before/after gate for this stage.
