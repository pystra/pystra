# PySTRA 2.0 migration plan

Status: migration commenced; integrated baseline and initial callable/class
naming pass, calibration replacement, and initial FORM result contract implemented,
6 September 2026. Integration branch: `v2.0`. Contributor policy: [CONTRIBUTING.md](../CONTRIBUTING.md).

**Design decisions, 10 September 2026:** class names follow PEP 8's acronym
rule (`FORM`, `SORM`, `PCESurrogate`, …); extreme-value distributions are named
by family (`Gumbel`, `GumbelMin`, `Frechet`, `Weibull`, `GEV`, `GEVMin`, with
`GEVmax` kept as an alias for `GEV`); the module reorganization ships in 2.0;
`pystra.active_learning` is a first-tier method package; `LimitState` stays with
`StochasticModel` in `model.py`; the minimum Python is 3.12; and
`cholesky_sensitivity` becomes private. See §4, §5, §7 (revised stages) and
§10, and the [programme review](v2.0-status-and-api-review.md).

**Scope:** a carefully validated implementation of established and selected
modern structural reliability methods, coupled with practical code calibration
and structural assessment tools.

**Recommendation:** make 2.0 the coherent, intentionally breaking API for
PySTRA's existing structural reliability methods and engineering workflows.
Integrate the open feature work first, preserve its numerical baseline, then
modernize names and the boundaries between models, algorithms, and results.
Keep the numerical implementations recognizable against their references.

**Release decision, 8 September 2026:** the outstanding PRs (#95, #96, #93,
#97 and #87) remain unmerged in 1.x. Their features, refinements and fixes are
v2.0 additions, as is the active-learning work from `al`. Present their final
v2 API as new release functionality, with contributor and literature credit.
The integrated development baseline is for numerical comparison; it is not
the API of a published 1.x release. The earlier #94 merge is recorded below
as a completed repository action, not an instruction to merge the remaining PRs.

## 1. Product boundary

PySTRA should be a canonical, inspectable implementation of traditional
structural reliability algorithms, with practical tools for code calibration
and structural assessment. For each method, document its formulation,
assumptions, numerical controls, failure modes, and reference benchmarks.

| Area | 2.0 scope |
| --- | --- |
| Reliability | FORM; both existing SORM fitting approaches and probability formulas; crude Monte Carlo; importance sampling; line sampling; subset simulation; reliability sensitivities |
| Systems and diagnostics | Component FORM, series/parallel tangent-event integration and bounds, existing topology helpers for original-event simulation, Strong Maximum Test |
| Probability modelling | Existing marginals, SciPy adapters, correlation handling, joint distributions and copulas from #96, Nataf and Rosenblatt transformations |
| Code calibration | Explicit load cases, Ferry-Borges-Castanheta processes, Turkstra combinations, normalized reliability and partial-factor calibration, target reliability |
| Assessment and decisions | Reusable case evaluation, resistance/load/model-uncertainty inputs, reference-period assumptions, design/risk studies, DDO and LQI tools already developed |

Preserve existing capabilities unless the API inventory explicitly records a
replacement or retirement. Copulas serve dependence modelling for reliability;
they do not create an obligation to add a general statistical modelling suite.

Exclude from the 2.0 critical path: general-purpose surrogate training,
general global sensitivity analysis, general Bayesian inference, copula fitting,
a general optimization framework, FE solver management, and a plugin registry.
Inspection-data updating, deterioration, time-dependent first-passage methods,
and additional classical reliability algorithms can be assessed separately
after this migration. External analyses remain callable through a small adapter.

## 4. Naming and public API policy

Apply the policy to the entire maintained codebase: public and private Python
code, parameters, attributes, tests, examples, notebook code cells, documentation,
and supported string keys. Retain mathematical notation in equations and
user-supplied variable names such as `R`, `G`, and `Q`.

Use lowercase modules and snake_case functions, methods, parameters, and
attributes; CapWords classes; UPPER_SNAKE_CASE module constants; `_` prefixes for
implementation details; properties for cheap data access; and verbs for work.
These conventions follow [PEP 8](https://peps.python.org/pep-0008/#naming-conventions).

Capitalize every letter of an acronym within a CapWords class name. PEP 8's
*Descriptive: Naming Styles* states: "When using acronyms in CapWords,
capitalize all the letters of the acronym. Thus HTTPServerError is better than
HttpServerError." Decided 10 September 2026: the rule applies uniformly, so
`Form`, `Sorm`, `FormResult`, `PceSurrogate`, `PceCandidate`, `PceFitResult`,
`PcKrigingSurrogate`, `PcKrigingFitResult` and `FbrLearning` become `FORM`,
`SORM`, `FORMResult`, `PCESurrogate`, `PCECandidate`, `PCEFitResult`,
`PCKrigingSurrogate`, `PCKrigingFitResult` and `FBRLearning`, alongside the
already-compliant `SystemFORM`, `FBCProcess`, `DDO`, `DDOCriterion`,
`DDOObjective`, `LQI`, `SWTP`, `SWTPRecord` and `SWTPIndexRecord`. This
supersedes the reversal in commit `0905fc5`. `ScipyDist` keeps its existing
spelling. Method, variable and module names use snake_case, including their
acronyms (`run_form`, `pc_kriging`).

Name extreme-value distributions by family, not by type numeral (decided
10 September 2026). The literature labels the three Fisher–Tippett limits with
Roman numerals — Type I (Gumbel), Type II (Fréchet) and Type III (Weibull), all
special cases of the GEV distribution — and 1.x followed it
(`TypeIlargestValue`, …). The initial v2 pass switched to Arabic numerals
(`Type1LargestValue`), which matches neither the literature nor 1.x; that
spelling is superseded. The bare family name is the conventional flavour —
maxima for Gumbel and Fréchet, minima for Weibull — and the opposite flavour
takes a `Min` or `Max` suffix. `Type1LargestValue` and `Type3SmallestValue` are
bit-identical to the existing `Gumbel` and `Weibull` (pdf, cdf and ppf,
including the Weibull shift) and are removed as duplicates. `Type2LargestValue`
becomes `Frechet`, the ASCII form of Fréchet, and `Type1SmallestValue` becomes
`GumbelMin`. Docstrings and the distribution guide give the Type I/II/III names
so that a search for "Type I extreme value" finds `Gumbel`. GEV follows the
same rule: `GEV` for maxima and `GEVMin` for minima, with `GEVmax` kept as a
permanent alias for `GEV` (decided 10 September 2026).

Use `std`, `start_point`, `limit_state`, `model`, `options`, `n_samples`,
`max_iterations`, `failure_probability`, and `reference_period` consistently.
Keep established technical names such as `pdf`, `cdf`, `ppf`, `beta`, `alpha`,
and coordinate names `x`, `u`, `z`. Prefer descriptive lowercase names for
compound quantities (`design_point_x`, `modified_correlation`, `cdf_gradient`).
Use `analyze` consistently in Python identifiers; prose can retain local spelling.

Use keyword-only configuration for algorithms and studies. Keep convenient
distribution construction such as `Normal("R", mean=100, std=10)`. Replace
`input_type` flags that reinterpret moments as parameters with native-parameter
keywords on the same constructor, such as `Gumbel("Q", loc=8.9, scale=1.56)`
(decided 11 September 2026, in place of `from_parameters(...)`); preserve each
distribution's exact
parameterization, bounds, shifts, and GEV shape convention.

Build a machine-readable migration manifest after all PRs land: old qualified
name/signature, new qualified name/signature, replacement kind, semantic notes,
and examples. Include public output/table columns and subclass hooks, not just
callable names. Review every apparent public helper: preserve it, give it a
documented replacement, or mark its removal explicitly. An AST count alone is
insufficient to decide the supported API.

Replace wildcard imports with explicit exports and `__all__`. Keep convenient
top-level imports for common modelling classes and algorithms; specialized
calibration, assessment, and decision tools have documented module paths.
Low-level integration, quadrature, and solver iteration helpers become private
unless they are intentionally supported extension points.

### Model and execution state

`StochasticModel` remains the familiar user-facing model. Its joint law owns
marginals and dependence; constants remain separate. The independent model
builder and the explicit `JointDistribution` route must share one source of
truth, with deterministic variable ordering and clear rules for modifications.
Validate duplicate names, parameter domains, and correlation dimensions before
running. Never reset user-supplied correlation silently when adding a variable.

Create a prepared run context containing the transformation, variable binding,
evaluation counters, RNG, and algorithm settings. Snapshot mutable input arrays
or version/invalidate cached preparation after edits. Repeated runs and
different algorithms sharing a model must not contaminate one another.
Constructors validate/store configuration; only `run()` performs analysis.

### Results and options

`run()` returns a typed result snapshot. Use a small common reliability result
contract and method-specific types (`FORMResult`, `SORMResult`,
`SimulationResult`, `SystemFORMResult`). Preserve arrays against later solver
mutation; a frozen dataclass alone does not make NumPy arrays immutable.

Common fields: `failure_probability`, `beta`, `status`, `message`,
`n_limit_state_evaluations`, method identity, effective options, and relevant
provenance. Algorithm-specific diagnostics remain typed: design points and
convergence residuals; SORM formula results and curvatures; sampling uncertainty
and termination reason; system component results and bounds. Strong Maximum
Test returns a diagnostic result, not a pretend probability estimate.

Define `beta = -Phi^-1(failure_probability)` consistently for reliability
results. In Student-t standard space, preserve the geometric/signed design
index separately as `design_index`, with `standard_space` metadata. Record this
as a semantic migration from #96's `getBeta()`/`getEquivalentBeta()` distinction.
SORM retains named results for each probability approximation; selecting a
primary formula must be explicit and preserve the current default route.

Invalid input raises a specific error. Numerical nonconvergence raises an
`AnalysisError` with diagnostic context by default; an explicit
`on_failure="return"` mode supports batch studies. Returned failed results
have a non-success status and unavailable probability/index fields. Budget
termination in simulation can retain a valid estimate with an unmet-precision
status; consumers must distinguish those cases. Never report failure as zero
probability or reuse a previous successful run's result.

Replace `AnalysisOptions` with small validated settings for FORM, SORM, and
each simulation/diagnostic method, composing genuinely shared evaluation and
transformation settings. Reject unknown options; do not silently ignore settings
that belong to another algorithm. Preserve old numerical defaults during the
rename stage; change defaults only in separately validated commits.

### Extension contracts and numerical conventions

Specify small typed interfaces where existing code needs substitution;
[Python protocols](https://docs.python.org/3/library/typing.html#typing.Protocol)
can express these without requiring users to inherit a large framework.

- **Marginal distribution:** density/CDF/quantile operations, moments, support,
  sampling, and explicit parameter replacement. Sensitivity capabilities and
  fixed constructor parameters are separate metadata. Replace fragile
  reconstruction via `_ctor_kwargs` with a documented copy/parameter-update
  contract, preserving shifted/bounded distributions and SciPy adapters.
- **Transformation:** physical/reference mappings, explicitly directed
  Jacobians (`jacobian_u_wrt_x`, `jacobian_x_wrt_u`), dimension, and reference
  space capabilities. Preserve physical-Pearson Gaussian Nataf calibration
  separately from direct copula shape/correlation parameters. Algorithms check
  that their required normal/independence assumptions hold before running.
- **Limit-state evaluator:** named callables, optional analytic gradient,
  numerical differentiation, and scalar/batch adaptation. Define boundary
  convention (`g <= 0` means failure), variable order, and gradient dimensions.
  Audit existing equality behavior before changing it, particularly for atoms.
- **Reliability evaluator for studies:** accept model/case inputs and return
  the common result contract. Calibration and assessment may default to FORM
  while accepting another suitable method or an external solver adapter.

Adopt public point shapes `(n_variables,)` and batch shapes
`(n_samples, n_variables)`, matching #96's joint samples. Batch limit-state
values have shape `(n_samples,)` and gradients `(n_samples, n_variables)`.
Keep current column-oriented kernels behind adapters until a separately tested
conversion is justified; never guess the orientation of a square array.

Use a local NumPy `Generator` throughout sampling and randomized integration;
accept `rng` as a seed, generator, or `None`, with documented ownership and
rerun behavior. Integer seeds recreate a stream per run; a supplied generator
advances its own state. Independent child streams support repeatable batches.
The migration changes legacy random sequences; validate statistical behavior,
and record the generator and dependency versions for reproducibility.
[NumPy's Generator documentation](https://numpy.org/doc/stable/reference/random/generator.html)
also makes clear that cross-version stream compatibility is not guaranteed.

Continuous transformations must continue to reject unsupported atomic/mixed
marginals. Preserve `ZeroInflated` through supported existing routes and state
its limitations; do not claim smooth FORM/CDF-gradient contracts apply at atoms.

### Rosenblatt ordering benchmark for both release lines

Meinen and Steenbergen (2025), Structural Safety 112, 102521
([DOI](https://doi.org/10.1016/j.strusafe.2024.102521)), is a system-level
validation reference. Three regressions in `tests/test_rosenblatt_system_order.py`
now reproduce Example 1's fully dependent identical events, demonstrate the
invalid mixed-order alpha aggregation, and check a distinct-component Gaussian
system under Nataf and both Rosenblatt orders. Original-event integration along
both physical coordinates supplies an order-independent reference. See the
[copula guide](source/copulas.rst) for values and an apparent transposition of
the paper's printed dependent-system Monte Carlo probabilities.

These tests also pass on the v1 copula feature commit `f3d0d1f` with API spelling
adaptation; backport them when integrating that feature into v1. No v1 PR was
changed by this benchmark work. The explicit copula/shared-model implementation
prevents inconsistent component coordinate aggregation, but non-Gaussian FORM
remains sensitive to order and retains its first-order approximation error.

Before accepting external/precomputed component results, the v2 result contract
must preserve joint-model identity, reference transformation and conditioning
order. Matching variable names and `standard_space` alone does not establish a
common coordinate system. Gaussian results may be aligned through an explicit
orthogonal mapping; a permutation of labels is insufficient in general.

The indexed [worked tutorial](source/notebooks/ex_rosenblatt_system_order.ipynb)
credits Nadieh Meinen and Raphaël Steenbergen prominently, reproduces the
transformation geometry and shared-event system, and adds Gaussian coordinate
alignment and original-event checks. It also covers independent copies using
the exact product formula and direct sampling of independent bivariate blocks.
The tutorial executes on v2 and, with API adaptation, on the v1 copula feature.

Next benchmarks: SystemFORM on explicit independent component blocks from
Example 1, followed by a selected nonlinear case from Example 2 with a completely
specified joint law and original-event simulation reference. Frank is currently bivariate, so
independent-block composition is a bounded prerequisite. Keep the paper's
local-component autocorrelation approximation separately identified; do not
silently present it as a full joint-copula system model. An order-sensitivity
report may be useful, but is not a certified bound or a factor-selection policy.

### Calibration, assessment, and presentation

Implementation status: the calibration replacement described below is now
implemented in the structural checkpoint above. The following design rationale
also describes remaining extension work, including alternative reliability
evaluators and broader assessment integration. The migration guide is the
source of truth for the current callable API.

**The primary code-calibration workflow is the normalized design study already
implemented by `CodeCalibration`.** Start with candidate code factors,
design over representative load ratios/cases, evaluate achieved reliability,
and compare or adjust the factors. Separate the probability model from factor
sets and return results with their analyzed inputs and convergence status.
Keep plotting outside the numerical workflow. The existing implementation
evaluates supplied factors; automated fitting requires a separately specified
objective and acceptance policy. See the [calibration review](calibration-review.md)
for reproduced correctness problems and the distinction between workflows.

**Replace the existing `Calibration` object as a 2.0 deliverable.** Renaming
its methods or moving the same stateful implementation into a package will not
meet this requirement. Preserve the numerical methods and their references,
while replacing their orchestration and data model. The current object mixes
target solving, design-point extraction, factor estimation, factor selection,
design checking, DataFrame mutation, and reporting. For example,
`get_design_param_factor()` depends on tables populated by an earlier `run()`,
and some helpers hard-code `z` despite accepting a calibration variable name.

Preserve this specialized inverse/design-point workflow through independently
usable operations; it does not prescribe the sequence for normalized reliability studies:

| Operation | Explicit inputs and outputs |
| --- | --- |
| Solve designs to a target | Named cases, design parameter, target, solve settings, reliability evaluator → per-case calibrated designs, reliability results, residuals, and solve status |
| Derive factors | Calibrated design points, nominal values, variable roles, coefficient/matrix method → per-case resistance, action, and combination factors |
| Select factors | Per-case factors and a named selection policy → a selected factor set with governing-case provenance |
| Verify factored designs | Selected factors, nominal values, design rule, and cases → achieved reliability and target margins for each resulting design |

Prefer small functions and value/result objects for these steps. A thin
`FactorCalibration` convenience runner may compose them if the prototype shows
that it improves the everyday example. It must not maintain a second copy of
the numerical logic or require users to invoke helpers in a hidden sequence.
Exact class/function names remain open for iteration.

Separate target-design solution methods (`optimize` and `alpha` today) from
factor-estimation methods (`matrix` and `coeff`). Keep both dimensions of the
existing method matrix covered. Factor aggregation is an engineering decision:
make minimum-resistance/maximum-action or combination selections explicit,
retain the governing cases, and re-evaluate the resulting factored designs.
Selecting extrema is not itself evidence that every case meets its target.

Use named variable roles and stable case/variable ordering. Numeric kernels
receive arrays and explicit metadata; DataFrames are input/output adapters,
not mutable storage coordinating the algorithm. Remove `dfXstarcal`-style
intermediate attributes from the public API. Remove pseudo-Hungarian type
prefixes throughout the codebase, including parameters, attributes, private
helpers, and local variables: `dict_nom` becomes `nominal_values`, for example.
Choose names by meaning and use annotations for types; simply stripping a
prefix from a cryptic abbreviation does not complete the naming migration.
Conventional `df` or a readable `factors_df` is acceptable for local DataFrames
in short pandas operations; retain semantic names for persistent/public data.
Neither the calibration variable
nor the resistance/action names may be hard-coded. Do not mutate a caller's
case, constants, distribution, or nominal-value mapping while trying designs.

Validate unknown methods, inconsistent labels, invalid nominals, singular
factor systems, and infeasible targets explicitly. Record root-solver status
and target residuals as well as inner reliability convergence. Bounded or
bracketed solving can be introduced where supported by the problem; do not
assume monotonic reliability or change the mathematical method during extraction.
Alternative reliability evaluators can serve target solving and verification;
design-point/alpha-based factor methods must declare their stronger capability
requirements and reject incompatible results clearly.

Use the existing linear/nonlinear, two/three-action calibration tests as the
preservation baseline. Add meaningful cases for a design parameter other than
`z`, reordered case/variable inputs, repeatability without input mutation,
infeasible targets, and nonconverged inner analyses. Verify achieved reliability
after factor selection, not only the factor tables. Share reliability-result
and evaluation conventions with the normalized reliability workflow where useful,
without forcing that workflow through design-point factor extraction. Add
direct normalized-model/study tests, including failed FORM, stale-input prevention,
analytic cases, and ratio-grid endpoints; tutorial execution alone is insufficient.

The replacement was implemented alongside the initial FORM result slice,
ahead of the broader stage 5 engineering-workflow work. The migration guide
and tutorials replace the legacy workflow, including downstream table use.

Preserve `LoadCombination`'s inspectable probabilistic cases and FBC/Turkstra
generation, while separating these from solver execution and code design
rules. Remove the legacy dictionary constructor and duplicate label state.
Case metadata must carry resistance/action roles and leading actions explicitly;
the current preferred `cases=` path does not preserve those roles for old
calibration. Named mappings remain appropriate for nominal values and cases;
fixed-schema model/factor/result concepts should have validated named fields.
Neither normalized reliability studies nor arbitrary assessment cases should require
the legacy load-combination schema. Reuse the study concepts in #93. Extract
a shared case evaluator only where it removes actual duplication. Preserve
design variables, calibrated factors, achieved reliability, convergence, and
failed cases in structured results. Store units/reference periods, dependence
assumptions, target sources, and model-error assumptions where applicable.

Assessment should make resistance/load scenarios and comparisons easy to run
and audit. It must not silently infer annual independence when converting
reference periods or present LQI targets as universal code requirements.
Preserve #93's distinction between source-table lookups and derived targets.

Core computation returns numbers and arrays. DataFrame output remains a
first-class convenience for engineering workflows, and plotting returns
Matplotlib objects without calling `show()` implicitly. Defer making pandas
and Matplotlib optional dependencies until import isolation is demonstrated;
dependency extras are not a prerequisite for the API migration.

## 6. Proposed everyday use

This is the eventual target API sketch, not the current development API.
See the migration guide for an executable example of the initial naming pass:

```python
import pystra as ra

model = ra.StochasticModel()
model.add_variable(ra.Normal("R", mean=100.0, std=10.0))
model.add_variable(ra.Normal("S", mean=60.0, std=12.0))

limit_state = ra.LimitState(lambda R, S: R - S)
result = ra.FORM(
    model=model,
    limit_state=limit_state,
    options=ra.FORMOptions(max_iterations=100),
).run()

print(result.beta)
print(result.failure_probability)
print(result.design_point_x)
print(result.summary())
```

Before freezing the design, exercise equivalent sketches for SORM reuse of a
FORM result, seeded simulation, system FORM, copula transformations, partial
factor calibration, a structural assessment case set, and DDO/LQI. These should
remain short, inspectable scripts. Avoid parallel functional and object APIs
unless a demonstrated workflow needs both.

## 9. User migration and release policy

Ship one canonical API in 2.0. Do not keep permanent camelCase aliases in the
main namespace. Maintain the final stable pre-2.0 line for critical fixes during
a proposed 12-month transition, with dated documentation and reproducible
installation instructions. The maintainer can adjust that support commitment
before release; it is not a promise already made to users.

No aliases does not mean no guidance. Each top-level module that 2.0 moves
keeps a stub at its 1.x path whose import raises `ImportError` naming the new
location — thirteen modules, all in v1.6.0: `analysis`, `cholesky_sensitivity`,
`correlation`, `form`, `integration`, `loadcomb`, `ls`, `mc`, `quadrature`,
`sensitivity`, `sorm`, `ss` and `transformation`. Modules added during 2.0
development were never released and need none. A package-level `__getattr__`,
generated from the naming maps, turns access to a renamed class or function
into an error naming its replacement. The four removed `distributions/type*`
modules get no stub: 1.x exported their classes from `pystra` and
`pystra.distributions`, where the class signposts apply. Signposts never return
the object, so they are not aliases; they are removed in 3.0. The one
deliberate alias is `GEVmax`, kept as another name for `GEV` at the
maintainer's request.

Provide a migration guide with before/after examples, an exhaustive symbol and
keyword map, import relocations, options/defaults, coordinate/index semantics,
result/table schemas, subclass hooks, and removed features. Explain that old
pickled solver objects are not portable; offer plain-data export where useful.
Ship a conservative syntax-aware codemod for unambiguous imports/calls/keywords,
with dry-run diffs. Flag getters-to-results, options splitting, shape changes,
and parameter-mode conversions for manual review. Never globally replace
arbitrary user function names, strings, or engineering symbols.

Release progression: internal integrated baseline → `2.0.0a1` after the core
API works → public beta with all capabilities and migration guide → RC with
API freeze → `2.0.0`. Give a small group of users representative calibration,
assessment, and external-solver scripts to exercise during beta. After API
freeze, defer elective restructuring and new algorithms to later releases.

Serve stable and 2.0 development documentation separately. Update versioning,
package metadata (including the README content type), badges, Python
classifiers, and changelog together at release preparation. Ensure development
branch workflows build artifacts without publishing stable documentation or
PyPI releases. The final `v2.0` → `main` integration and release publication are
distinct from developing and testing the migration.

## Stage 4 design (11 September 2026)

The concrete API for stage 4, following §5. Names marked * are introduced here
under the plan's general descriptions (a PySTRA exception hierarchy, per-method
settings, a Strong Maximum diagnostic result); the others are named elsewhere
in this plan.

**Errors.** `PystraError`* is the base class. `ModelError`* is also a
`ValueError` and reports invalid model, distribution or input specifications.
`AnalysisError` is also a `RuntimeError`: an analysis could not produce a valid
result, and the error carries that result in `.result` for diagnosis. All three
are exported from `pystra`.

**Constructors.** `Analysis(model, limit_state, *, options=None, on_failure="raise", ...)`,
with `model` and `limit_state` required. Method-specific settings are
keyword-only: `SORM(..., form=None)`, `CrudeMonteCarlo(..., rng=None)`,
`ImportanceSampling(..., form=None, rng=None)`, `DistributionAnalysis(..., rng=None)`,
`LineSampling(..., form=None, rng=None)`,
`SubsetSimulation(..., p0=0.1, proposal_sigma=1.0, rng=None)`,
`SensitivityAnalysis(..., method="numerical", delta=0.01)`,
`SystemFORM(model, system, *, options=None, maxpts=..., abseps=..., releps=...)`,
`StrongMaximumTest(form=None, *, model=None, limit_state=None, design_point=None, options=None, ..., rng=None)`
and `ActiveLearning(model, limit_state, *, options=None, ..., rng=None)`.
Constructors only validate and store; `run()` does the work, so SORM,
importance sampling and line sampling no longer run FORM when constructed.

**Options** are frozen dataclasses that reject unknown fields and keep the 1.x
numerical defaults:

- `FORMOptions(max_iterations=100, limit_state_tolerance=1e-3, gradient_tolerance=1e-3, step_size=0, differentiation="ffd", ffd_parameter=1000, block_size=1000, transform=None, rosenblatt_order=None)`
  for FORM and the design-point methods built on it (system FORM, sensitivity,
  Strong Maximum Test);
- `SORMOptions(fit="curve", formula="breitung", ffd_parameter=1000, form=FORMOptions())`;
- `SimulationOptions`*`(n_samples=100_000, block_size=1000, target_cov=0.05, sampling_std=1.0, bins=None, transform=None, rosenblatt_order=None)`
  for the simulation methods and active learning; a method rejects a setting it
  does not use.

`AnalysisOptions` is removed and signposted, together with its dead fields
(`transf_type`, `Ro_method`, `flag_sens`, `Recorded_u`, `Recorded_x`,
`ffdpara_thetag`, `sim_point`, `multi_proc`, `random_generator`). Analyses no
longer print; results provide `summary()`.

**Results** are frozen, vector fields are read-only arrays, and `run()` returns
them. Common fields: `method`, `status`, `message`, `failure_probability`,
`beta`, `n_limit_state_evaluations`, `variable_names` and `options`, with
`converged` and `summary()`.

- `FORMResult`: `design_index`, `design_point_x`, `design_point_u`, `alpha`,
  `standard_space`, `iterations`, `limit_state_error`, `direction_error`, and
  `to_dataframe()`.
- `SORMResult`: `form` (a `FORMResult`), `fit`, `curvatures`, `formula` and
  `approximations` (named probabilities, `breitung` and `modified_breitung`;
  the primary formula is Breitung, the current route).
- `SimulationResult`: `coefficient_of_variation`, `n_samples` and method-specific
  `diagnostics` (subset levels, the line-sampling direction).
- `SystemFORMResult`: `bounds`, `component_results` and `correlation`.
- `SensitivityResult`*, `StrongMaximumResult`* (a diagnostic, not a
  probability) and `DistributionAnalysisResult`*.

`status` is `converged`, `not_converged`, `completed` or `precision_not_met`
(a simulation reached its sample budget before `target_cov`).

**Failure.** Nonconvergence raises `AnalysisError` unless `on_failure="return"`,
which returns a result with a non-success status and no probability, for batch
studies such as calibration.

**Randomness.** `rng` accepts a seed, a `Generator` or `None`. An integer seed
recreates the stream on every `run()`; a supplied generator advances its own
state. This changes the legacy random sequences, so simulation tests are
validated statistically rather than by exact values.

**Evaluation.** `LimitState` keeps only its specification. Evaluation settings
and the evaluation counter belong to each run, so repeated runs and different
analyses sharing a model cannot contaminate one another.

**CorrelationMatrix** is validated on construction (square, symmetric, unit
diagonal, positive definite) and gains `cholesky()`,
`nearest_positive_definite()`* and `nataf(model)`*. It is the preferred input
to `set_correlation`, which validates array input the same way.

**Models and distributions** follow the §4 table: `std`, `start_point`,
`Constant(name, value)`, `mean` and `std` properties, `model.variable(name)`,
a read-only `model.constants`, and native-parameter keywords replacing
`input_type`, in place of the planned `from_parameters(...)` constructors. These parameter renames belonged to stage 2's scope and were not
done there.

Sequence, one commit per step behind the stage-4 gate: errors; evaluation
state; results; options and constructors; randomness; private internals and
removal of getters and printing; failure handling; CorrelationMatrix; models
and distributions; version `2.0.0a1`.

## Active-learning reliability in v2.0

The maintainer has confirmed that surrogate-assisted reliability belongs in
**v2.0**. Keep the coherent implementation on this branch and retain the
optional `al` dependency extra for Kriging. Active learning is new in v2.0
and remains unmerged in 1.x. The v2.0 branch remains the integration branch;
do not open a migration PR yet.

The `al` branch is integrated with its ancestry retained. Scope is AK-MCS-style
reliability with Kriging and adaptive sparse bootstrap Hermite PCE.
PC-Kriging was outside the initial sparse-PCE increment; its subsequent
implementation and the other approved additions are recorded below. The tutorial credits Echard et al., Bichon et al., Marelli and
Sudret, and Moustapha et al.; it states the differences from their algorithms.
Benchmark gates use three seeds, analytic normal-sum/lognormal-beam references,
rotated-coordinate four-branch quadrature, and independent classification checks.
GPL-3.0-or-later metadata and documentation follow the retained licence notice.

Sparse PCE now adapts UQLab 2.2.0 hybrid-LARS, degree/q-norm selection and
selected-support bootstrap. See [source provenance](uqlab-pce-provenance.md)
for exact source hashes, retained notices, numerical differences and executed
UQLab/Octave parity fixtures. Dense OLS remains explicit. Batch enrichment and
full bootstrap reselection are not part of this increment.

## Literature-guided active-learning coverage

The complementary reviews are Teixeira, Nogal and O’Connor (2021),
*Structural Safety* 89, 102019, doi:10.1016/j.strusafe.2020.102019; and
Moustapha, Marelli and Sudret (2022), *Structural Safety* 96, 102174,
doi:10.1016/j.strusafe.2021.102174. Both are now cited in the user documentation.

[Coverage and implementation sequence](source/active_learning.rst) distinguishes
completed components from missing combinations. The coherent four-component
design and the subsequent active subset simulation, PC-Kriging, FBR learning
and active importance sampling increments are implemented for v2.0, with
validation recorded below. This is not a commitment to port
every reviewed variant. Classical adaptive response surfaces
and SVM classification remain candidates for later assessment-specific needs.

The first component increment is implemented: `pystra.active_learning` is a
package with separate surrogate, learning, estimation, stopping and result
modules, retaining the existing public import path. `LearningFunction`,
`ReliabilityEstimator` and `StoppingCriterion` complement `Surrogate`.
Default U/EFF selection, fixed-pool enrichment and independent final MC retain
their numerical behaviour. Explicit components reject conflicting shortcut
settings. Estimators own their uncertainty calculations; the runner does not
assume that a custom estimate has independent binomial sampling error.

The history now records probability/beta bands based on mean +/- 2 std.
`BetaBounds` and `BetaStability` implement the review's equations and consecutive
fit requirements, with `AllCriteria` for combined policies. These diagnostics
do not certify the true failure probability; sampling error remains separate.
The result stores one immutable `ReliabilityEstimate` and exposes its familiar
probability, beta and sampling properties. See the migration guide for the
result serialization and configuration changes.

The next tranche is implemented: `SubsetSimulationEstimator` now generates
nested populations after each fit through `EnrichmentEstimator`, returning
selection points separately from measure-correct probability diagnostics.
Exploration conditions on mean - 2 std, preserving nested mean +/- 2 std
failure events. Independent final runs classify the frozen mean. The pCN
kernel preserves the normal prior; replicated runs and chain clusters supply
sampling error diagnostics without an IID binomial interval. Level-budget and
stalled-threshold failures stay visible. The standalone subset solver remains
an unchanged baseline.

Validation covers rare linear and disconnected two-tail/four-branch active
problems at three seeds, independent weighted or direct classification checks,
conditional-normal invariance, and replicated rare-event accuracy/uncertainty
in 2 and 20 dimensions. The new active-subset tutorial cites Au and Beck,
Cotter et al. and both active-learning reviews, and distinguishes this variant
from their original settings. This does not reproduce the full review benchmark.

The subsequent PC-Kriging, FBR and active-IS additions are recorded below.

### Published benchmark tutorials

Added the Marelli–Sudret (2018) 23-bar truss and the explicit UQLab hat
function. The truss has independent stiffness-assembly checks, conditional
probability integration, published FORM/SORM comparisons and a three-seed
active-PCE benchmark. The hat has a rotated-coordinate quadrature reference,
independent importance-sampling validation and exact cubic recovery checks.
Both tutorials state physical settings, algorithm variants, uncertainty
semantics and source provenance. The review supplement's conflicting hat /
four-branch probabilities are documented without assuming a correction.
These extend benchmark coverage; the subsequent algorithm tranche is below.

### PC-Kriging, FBR and active importance sampling

Implemented the three agreed additions: sequential PC-Kriging with universal
trend uncertainty, actual bootstrap voting with probability-range stopping,
and active importance sampling with explicit Gaussian-mixture proposals and
weighted diagnostics. Existing U/EFF and fixed-MC defaults remain unchanged.
New contracts are recorded in the migration guide and API migration manifest.
The provenance note documents UQLab numerical comparisons and algorithm variants.

Tests cover all four branches with PC-Kriging, the lognormal beam with FBR,
rare one- and two-region active-IS problems, independent rare-event integration,
likelihood gradients, predictor constraints and explicit incomplete results.
System-specific active learning, batch enrichment and automatic proposal
adaptation remain potential later work, outside these three additions.
