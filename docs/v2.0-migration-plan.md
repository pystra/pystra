# PySTRA 2.0 migration plan

Status: overall sequence accepted; API details remain iterative, 6 September
2026. Planning branch: `v2.0`. Contributor policy: [CONTRIBUTING.md](../CONTRIBUTING.md).

**Recommendation:** make 2.0 the coherent, intentionally breaking API for
PySTRA's existing structural reliability methods and engineering workflows.
Integrate the open feature work first, preserve its numerical baseline, then
modernize names and the boundaries between models, algorithms, and results.
Keep the numerical implementations recognizable against their references.

This document specifies future work and records integration progress. The
initial planning commits did not merge PRs, rename APIs, or change the package
version. Subsequent integration progress is recorded below.

## 1. Product boundary

PySTRA should be a canonical, inspectable implementation of traditional
structural reliability algorithms, with practical tools for code calibration
and structural assessment. For each method, document its formulation,
assumptions, numerical controls, failure modes, and reference benchmarks.

| Area | 2.0 scope |
| --- | --- |
| Reliability | FORM; both existing SORM fitting approaches and probability formulas; crude Monte Carlo; importance sampling; line sampling; subset simulation; reliability sensitivities |
| Systems and diagnostics | Component FORM, series/parallel tangent-event integration and bounds, existing topology helpers for original-event simulation, Strong Maximum Test |
| Probability modelling | Existing marginals, SciPy adapters, correlation handling, joint distributions and copulas from #96, Nataf and Rosenblatt transformations |
| Code calibration | Explicit load cases, Ferry-Borges-Castanheta processes, Turkstra combinations, partial-factor and generic calibration, target reliability |
| Assessment and decisions | Reusable case evaluation, resistance/load/model-uncertainty inputs, reference-period assumptions, design/risk studies, DDO and LQI tools already developed |

Preserve existing capabilities unless the API inventory explicitly records a
replacement or retirement. Copulas serve dependence modelling for reliability;
they do not create an obligation to add a general statistical modelling suite.

Exclude from the 2.0 critical path: polynomial chaos, surrogate training,
general global sensitivity analysis, general Bayesian inference, copula fitting,
a general optimization framework, FE solver management, and a plugin registry.
Inspection-data updating, deterioration, time-dependent first-passage methods,
and additional classical reliability algorithms can be assessed separately
after this migration. External analyses remain callable through a small adapter.

### Readiness before the breaking migration

The release/tag inventory still ends at
[v1.6.0](https://github.com/pystra/pystra/releases/tag/v1.6.0); there is no
published v2.x series as of this audit. No additional algorithm is a prerequisite
for beginning 2.0. Complete the feature stack and a focused correctness pass
before freezing the pre-rename numerical baseline.

Two concrete defects were reproduced on the #94-integrated source:

- **Propagation of failed FORM results:** for independent standard-normal
  `X`, `Y` and `g = 5 - X - Y`, forcing one FORM iteration leaves FORM
  nonconverged. SORM nevertheless reports `results_valid=True` and Breitung
  failure probability `0.5`; the analytic probability is approximately
  `0.000203476`. Reject invalid prerequisites before computing results. Audit
  line sampling, importance sampling, and calibration for the same dependency
  on unchecked FORM output. Add focused regression tests before refactoring.
- **No observed Monte Carlo failures:** 100 crude Monte Carlo samples of
  `g = 1` return `failure_probability=0` and `beta=0`. The latter contradicts
  the probability/index relationship. Correct the index handling and clearly
  distinguish a zero observed-failure estimate from evidence of zero risk.
  Include an appropriate finite-sample upper bound for crude Monte Carlo;
  do not reuse its independent-Bernoulli formula for weighted or dependent
  simulation estimators. Test all-failure and exhausted-budget cases too.

These are readiness findings, not fixes already implemented. Make the small
correctness changes separate from API renaming and capture their corrected
reference outputs. A final pre-2.0 public release is useful if maintainers want
users to receive the accumulated features/fixes before porting scripts; choose
its version after auditing compatibility of already merged API cleanup. An
internal, reproducible baseline is sufficient to begin migration development.

The only open non-PR issue at this audit is
[#79, CalculiX coupling](https://github.com/pystra/pystra/issues/79).
An external-solver callable example would help assessment users and exercise
the evaluator boundary. A dedicated FE integration subsystem is not a release
prerequisite. Promote the existing OpenSeesPy example only after checking its
dependencies, execution, and scope.

## 4. Naming and public API policy

Apply the policy to the entire maintained codebase: public and private Python
code, parameters, attributes, tests, examples, notebook code cells, documentation,
and supported string keys. Retain mathematical notation in equations and
user-supplied variable names such as `R`, `G`, and `Q`.

Use lowercase modules and snake_case functions, methods, parameters, and
attributes; CapWords classes; UPPER_SNAKE_CASE module constants; `_` prefixes for
implementation details; properties for cheap data access; and verbs for work.
These conventions follow [PEP 8](https://peps.python.org/pep-0008/#naming-conventions).

For acronym class names, adopt the explicit project choice `Form`, `Sorm`,
`SystemForm`, `GevMax`, `GevMin`, `FbcProcess`, `Ddo`, `Lqi`, and `Swtp`.
This extends the existing `Form`/`Sorm` style consistently; it is a project
choice rather than a claim that PEP 8 requires this acronym spelling.
Documentation continues to use FORM, SORM, LQI, etc. for the methods.

Use `std`, `start_point`, `limit_state`, `model`, `options`, `n_samples`,
`max_iterations`, `failure_probability`, and `reference_period` consistently.
Keep established technical names such as `pdf`, `cdf`, `ppf`, `beta`, `alpha`,
and coordinate names `x`, `u`, `z`. Prefer descriptive lowercase names for
compound quantities (`design_point_x`, `modified_correlation`, `cdf_gradient`).
Use `analyze` consistently in Python identifiers; prose can retain local spelling.

Representative mapping, subject to the full post-integration inventory:

| Existing API | Proposed 2.0 API | Migration kind |
| --- | --- | --- |
| `model.addVariable(rv)` | `model.add_variable(rv)` | Rename |
| `model.getVariable(name)` | `model.variable(name)` | Lookup method |
| `model.getConstants()` | `model.constants` | Read-only view |
| `model.setCorrelation(matrix)` | `model.set_correlation(matrix)` | Validated mutation with cache invalidation |
| `dist.getMean()`, `dist.getStdv()` | `dist.mean`, `dist.std` | Properties; constructor keyword also changes |
| `startpoint`, `getStartPoint()` | `start_point` | Keyword/property |
| `Constant(name, val=...)` | `Constant(name, value=...)` | Keyword/property |
| `setImax(100)`, `setE1(...)`, `setE2(...)` | `FormOptions(max_iterations=100, limit_state_tolerance=..., gradient_tolerance=...)` | Options redesign; preserve equations and defaults |
| `getFailure()` | `result.failure_probability` | Result access |
| `getBeta()` | `result.beta` | Normal-equivalent result index; see semantics below |
| `getDesignPoint()` / `getDesignPoint(False)` | `result.design_point_u` / `result.design_point_x` | Explicit coordinates; vectors become 1-D |
| `getAlpha()` | `result.alpha`, paired with `result.variable_names` | Explicit order; named export available |
| `getNoFunctionCalls()` | `result.n_limit_state_evaluations` | Per-run count; distinguish batch invocations |
| `showResults()` / `showDetailedOutput()` | `result.summary()` / `result.to_dataframe()` | Return text/table; caller prints |
| `SystemFORM`, `GEVmax`, `ScipyDist` | `SystemForm`, `GevMax`, `ScipyDistribution` | Class names |
| `TypeIIlargestValue`, `TypeIIIsmallestValue` | `Type2LargestValue`, `Type3SmallestValue` | Consistent class words and numeric type labels |
| `dF_dtheta()` | `cdf_gradient()` | Rename extension method, preserve parameter-key meaning |
| `joint.getTransformation(...)` (#96) | `joint.make_transformation(...)` | Factory, not cheap property |
| `dict_dist_comb` / `dict_comb_cases` | `LoadCombination(cases=...)` or `.turkstra(...)` | Remove deprecated construction route |

Use keyword-only configuration for algorithms and studies. Keep convenient
distribution construction such as `Normal("R", mean=100, std=10)`. Replace
`input_type` flags that reinterpret moments as parameters with documented
`from_parameters(...)` constructors; preserve each distribution's exact
parameterization, bounds, shifts, and GEV shape convention.

Build a machine-readable migration manifest after all PRs land: old qualified
name/signature, new qualified name/signature, replacement kind, semantic notes,
and examples. Include public output/table columns and subclass hooks, not just
callable names. Review every apparent public helper: preserve it, give it a
documented replacement, or mark its removal explicitly. An AST count alone is
insufficient to decide the supported API.

Replace wildcard imports with explicit exports and `__all__`. Keep convenient
top-level imports for common modelling classes and algorithms; specialized
calibration, assessment, and decision tools have documented module paths.
Low-level integration, quadrature, and solver iteration helpers become private
unless they are intentionally supported extension points.

## 5. Architecture: small, explicit boundaries

Retain the `src` layout and the existing numerical kernels. Proposed dependency
direction is **engineering workflows → reliability algorithms → modelling and
numerics**. Reporting consumes results. Lower layers must not import workflows.

| Proposed location | Responsibility / current source |
| --- | --- |
| `model.py`, `limit_state.py` | Model specification, constants, named function binding; split evaluation concerns out of current `model.py` |
| `distributions/` | Marginals and SciPy adapter; rename compound filenames consistently |
| `dependence/` | Correlation, copulas, joint distributions, Nataf/Rosenblatt transforms from existing code and #96 |
| `reliability/` | `form.py`, `sorm.py`, `monte_carlo.py`, `importance_sampling.py`, `line_sampling.py`, `subset_simulation.py`, `system_form.py`, `strong_maximum.py`, `sensitivity.py` |
| `systems.py` | Component and event topology; reusable by FORM and simulation |
| `loads.py` | FBC processes and explicit load combinations |
| `calibration/` | Existing factor calibration and generic calibration, split by responsibility |
| `assessment.py` | Shared case/study evaluation and result collection extracted from existing workflows |
| `decision/` | Existing DDO objectives, LQI/SWTP criteria, target models, source records |
| `results.py`, `options.py`, `_numerics/` | Public result/options types and private shared kernels |
| `reporting.py` | Text, DataFrame, and plotting adapters |

Move files in a separate review step from renaming or changing numerical
behavior. Avoid exposing a generic `core` framework or introducing a public
class for every internal helper.

### Model and execution state

`StochasticModel` remains the familiar user-facing model. Its joint law owns
marginals and dependence; constants remain separate. The independent model
builder and the explicit `JointDistribution` route must share one source of
truth, with deterministic variable ordering and clear rules for modifications.
Validate duplicate names, parameter domains, and correlation dimensions before
running. Never reset user-supplied correlation silently when adding a variable.

Create a prepared run context containing the transformation, variable binding,
evaluation counters, RNG, and algorithm settings. Snapshot mutable input arrays
or version/invalidate cached preparation after edits. Repeated runs and
different algorithms sharing a model must not contaminate one another.
Constructors validate/store configuration; only `run()` performs analysis.

### Results and options

`run()` returns a typed result snapshot. Use a small common reliability result
contract and method-specific types (`FormResult`, `SormResult`,
`SimulationResult`, `SystemFormResult`). Preserve arrays against later solver
mutation; a frozen dataclass alone does not make NumPy arrays immutable.

Common fields: `failure_probability`, `beta`, `status`, `message`,
`n_limit_state_evaluations`, method identity, effective options, and relevant
provenance. Algorithm-specific diagnostics remain typed: design points and
convergence residuals; SORM formula results and curvatures; sampling uncertainty
and termination reason; system component results and bounds. Strong Maximum
Test returns a diagnostic result, not a pretend probability estimate.

Define `beta = -Phi^-1(failure_probability)` consistently for reliability
results. In Student-t standard space, preserve the geometric/signed design
index separately as `design_index`, with `standard_space` metadata. Record this
as a semantic migration from #96's `getBeta()`/`getEquivalentBeta()` distinction.
SORM retains named results for each probability approximation; selecting a
primary formula must be explicit and preserve the current default route.

Invalid input raises a specific error. Numerical nonconvergence raises an
`AnalysisError` with diagnostic context by default; an explicit
`on_failure="return"` mode supports batch studies. Returned failed results
have a non-success status and unavailable probability/index fields. Budget
termination in simulation can retain a valid estimate with an unmet-precision
status; consumers must distinguish those cases. Never report failure as zero
probability or reuse a previous successful run's result.

Replace `AnalysisOptions` with small validated settings for FORM, SORM, and
each simulation/diagnostic method, composing genuinely shared evaluation and
transformation settings. Reject unknown options; do not silently ignore settings
that belong to another algorithm. Preserve old numerical defaults during the
rename stage; change defaults only in separately validated commits.

### Extension contracts and numerical conventions

Specify small typed interfaces where existing code needs substitution;
[Python protocols](https://docs.python.org/3/library/typing.html#typing.Protocol)
can express these without requiring users to inherit a large framework.

- **Marginal distribution:** density/CDF/quantile operations, moments, support,
  sampling, and explicit parameter replacement. Sensitivity capabilities and
  fixed constructor parameters are separate metadata. Replace fragile
  reconstruction via `_ctor_kwargs` with a documented copy/parameter-update
  contract, preserving shifted/bounded distributions and SciPy adapters.
- **Transformation:** physical/reference mappings, explicitly directed
  Jacobians (`jacobian_u_wrt_x`, `jacobian_x_wrt_u`), dimension, and reference
  space capabilities. Preserve physical-Pearson Gaussian Nataf calibration
  separately from direct copula shape/correlation parameters. Algorithms check
  that their required normal/independence assumptions hold before running.
- **Limit-state evaluator:** named callables, optional analytic gradient,
  numerical differentiation, and scalar/batch adaptation. Define boundary
  convention (`g <= 0` means failure), variable order, and gradient dimensions.
  Audit existing equality behavior before changing it, particularly for atoms.
- **Reliability evaluator for studies:** accept model/case inputs and return
  the common result contract. Calibration and assessment may default to FORM
  while accepting another suitable method or an external solver adapter.

Adopt public point shapes `(n_variables,)` and batch shapes
`(n_samples, n_variables)`, matching #96's joint samples. Batch limit-state
values have shape `(n_samples,)` and gradients `(n_samples, n_variables)`.
Keep current column-oriented kernels behind adapters until a separately tested
conversion is justified; never guess the orientation of a square array.

Use a local NumPy `Generator` throughout sampling and randomized integration;
accept `rng` as a seed, generator, or `None`, with documented ownership and
rerun behavior. Integer seeds recreate a stream per run; a supplied generator
advances its own state. Independent child streams support repeatable batches.
The migration changes legacy random sequences; validate statistical behavior,
and record the generator and dependency versions for reproducibility.
[NumPy's Generator documentation](https://numpy.org/doc/stable/reference/random/generator.html)
also makes clear that cross-version stream compatibility is not guaranteed.

Continuous transformations must continue to reject unsupported atomic/mixed
marginals. Preserve `ZeroInflated` through supported existing routes and state
its limitations; do not claim smooth FORM/CDF-gradient contracts apply at atoms.

### Calibration, assessment, and presentation

**Replace the existing `Calibration` object as a 2.0 deliverable.** Renaming
its methods or moving the same stateful implementation into a package will not
meet this requirement. Preserve the numerical methods and their references,
while replacing their orchestration and data model. The current object mixes
target solving, design-point extraction, factor estimation, factor selection,
design checking, DataFrame mutation, and reporting. For example,
`get_design_param_factor()` depends on tables populated by an earlier `run()`,
and some helpers hard-code `z` despite accepting a calibration variable name.

Design the replacement around independently usable operations:

| Operation | Explicit inputs and outputs |
| --- | --- |
| Solve designs to a target | Named cases, design parameter, target, solve settings, reliability evaluator → per-case calibrated designs, reliability results, residuals, and solve status |
| Derive factors | Calibrated design points, nominal values, variable roles, coefficient/matrix method → per-case resistance, action, and combination factors |
| Select factors | Per-case factors and a named selection policy → a selected factor set with governing-case provenance |
| Verify factored designs | Selected factors, nominal values, design rule, and cases → achieved reliability and target margins for each resulting design |

Prefer small functions and value/result objects for these steps. A thin
`FactorCalibration` convenience runner may compose them if the prototype shows
that it improves the everyday example. It must not maintain a second copy of
the numerical logic or require users to invoke helpers in a hidden sequence.
Exact class/function names remain open for iteration.

Separate target-design solution methods (`optimize` and `alpha` today) from
factor-estimation methods (`matrix` and `coeff`). Keep both dimensions of the
existing method matrix covered. Factor aggregation is an engineering decision:
make minimum-resistance/maximum-action or combination selections explicit,
retain the governing cases, and re-evaluate the resulting factored designs.
Selecting extrema is not itself evidence that every case meets its target.

Use named variable roles and stable case/variable ordering. Numeric kernels
receive arrays and explicit metadata; DataFrames are input/output adapters,
not mutable storage coordinating the algorithm. Remove `dfXstarcal`-style
intermediate attributes from the public API. Neither the calibration variable
nor the resistance/action names may be hard-coded. Do not mutate a caller's
case, constants, distribution, or nominal-value mapping while trying designs.

Validate unknown methods, inconsistent labels, invalid nominals, singular
factor systems, and infeasible targets explicitly. Record root-solver status
and target residuals as well as inner reliability convergence. Bounded or
bracketed solving can be introduced where supported by the problem; do not
assume monotonic reliability or change the mathematical method during extraction.
Alternative reliability evaluators can serve target solving and verification;
design-point/alpha-based factor methods must declare their stronger capability
requirements and reject incompatible results clearly.

Use the existing linear/nonlinear, two/three-action calibration tests as the
preservation baseline. Add meaningful cases for a design parameter other than
`z`, reordered case/variable inputs, repeatability without input mutation,
infeasible targets, and nonconverged inner analyses. Verify achieved reliability
after factor selection, not only the factor tables. Adapt `GenericCalibration`
to reuse the same case evaluation and result conventions; keep its plotting
outside its numerical calculations.

Prototype this replacement in stage 1 alongside FORM, then implement it in
stage 5 after the runtime contracts stabilize. The migration guide must replace
the full legacy calibration workflow, including downstream use of its tables.

Reuse `LoadCombination`'s explicit cases and the study concepts in #93. Extract
a shared case evaluator only where it removes actual duplication. Preserve
design variables, calibrated factors, achieved reliability, convergence, and
failed cases in structured results. Store units/reference periods, dependence
assumptions, target sources, and model-error assumptions where applicable.

Assessment should make resistance/load scenarios and comparisons easy to run
and audit. It must not silently infer annual independence when converting
reference periods or present LQI targets as universal code requirements.
Preserve #93's distinction between source-table lookups and derived targets.

Core computation returns numbers and arrays. DataFrame output remains a
first-class convenience for engineering workflows, and plotting returns
Matplotlib objects without calling `show()` implicitly. Defer making pandas
and Matplotlib optional dependencies until import isolation is demonstrated;
dependency extras are not a prerequisite for the API migration.

## 6. Proposed everyday use

This is a target API sketch, not code that executes on the planning branch:

```python
import pystra as ra

model = ra.StochasticModel()
model.add_variable(ra.Normal("R", mean=100.0, std=10.0))
model.add_variable(ra.Normal("S", mean=60.0, std=12.0))

limit_state = ra.LimitState(lambda R, S: R - S)
result = ra.Form(
    model=model,
    limit_state=limit_state,
    options=ra.FormOptions(max_iterations=100),
).run()

print(result.beta)
print(result.failure_probability)
print(result.design_point_x)
print(result.summary())
```

Before freezing the design, exercise equivalent sketches for SORM reuse of a
FORM result, seeded simulation, system FORM, copula transformations, partial
factor calibration, a structural assessment case set, and DDO/LQI. These should
remain short, inspectable scripts. Avoid parallel functional and object APIs
unless a demonstrated workflow needs both.

## 7. Implementation sequence and acceptance gates

Each row is a reviewable work package; split large rows into several PRs.
Implementation branches target `v2.0`. Keep mathematical changes out of rename
commits, and keep each merged package runnable.

| Stage | Work and deliverables | Gate before proceeding |
| --- | --- | --- |
| 0. Integrated baseline | Merge the five PRs in section 3; enable CI on `v2.0`; preserve exact dependency versions and benchmark outputs | Combined suite and feature tutorials pass; integrated SHAs and unresolved limitations recorded |
| 1. API contract | Complete migration manifest; agree exports, names, options, result/error semantics, shapes, acronym rule; prototype the replacement calibration workflow | Every existing supported entry point has a disposition; examples cover all product areas |
| 2. Naming migration | Apply one-to-one renames to symbols, parameters, attributes, private code, examples, tests, and notebook source | Naming/import checks pass; deterministic outputs match stage 0 through the mapping |
| 3. Module organization | Move implementations to agreed modules; replace wildcard exports; establish dependency direction | Import smoke tests and built-wheel imports work; unchanged numerical baseline |
| 4. Runtime contracts | Introduce result snapshots, per-method settings, explicit execution, evaluator adapters, prepared state, transformation capabilities, and RNG ownership | Rerun/isolation/error/shape tests pass; each intentional behavior change documented and validated separately |
| 5. Engineering workflows | Replace `Calibration` with the explicit solve/derive/select/verify workflow; migrate load combinations, generic calibration, assessment/studies, DDO, and reporting; remove deprecated constructors | Existing calibration methods and DDO examples reproduce; selected-factor designs are verified; failed analyses remain visible |
| 6. Migration and release candidate | Complete guide/codemod, executable tutorials, API/theory docs, packaging checks, support matrix, release notes | All release gates below pass on the release commit; representative user scripts migrate successfully |

Stages 2–4 are the highest-risk work and should consume most of the effort.
Stage 2 preserves call/return behavior: getter-to-property/result conversions,
options splitting, and scalar/array changes belong to stage 4. Any intermediate
snake_case getter is transitional development code, not the final public API.
Start with a vertical slice (Normal model → FORM → result → one calibration
case) to verify stage 1's contract before propagating the structural refactor.
Any scaffolding aliases used inside the integration branch must have an owner
and removal gate before the first public beta.

For numerical verification, retain two environments: the integrated pre-rename

## 8. Definition of done

- **Numerical reference matrix:** analytic normal FORM and correlated linear
  cases; known SORM surfaces for both fitting methods/formulas; transformation
  round trips and Jacobians; distribution tails and parameter reconstruction;
  analytic versus numerical sensitivity; exact system half-spaces including
  singular directions; rare-event tails; #96's Student-t and Frank benchmarks;
  Strong Maximum diagnostic limitations; load/calibration and #93 DDO examples.
- **Method assumptions:** retain distinction between tangent-event system
  bounds and the original nonlinear event; Strong Maximum is a diagnostic,
  not a certificate; Student-t spherical coordinates are not independent
  normals. Include negative tests for unsupported combinations.
- **Simulation validation:** seeded reproducibility within a pinned environment,
  statistical comparisons with analytic/reference probabilities, budgets,
  uncertainty estimates, zero observed failures, and multiple failure regions.
  Use confidence-based acceptance rather than exact random output matching.
- **Runtime and extension behavior:** repeat runs, model mutations, shared
  inputs, external limit-state functions, DDM and finite differences, batch
  dimensions, stopping/error status, and custom distribution reconstruction.
- **Performance:** compare FORM evaluation counts, transform preparation,
  sampling throughput, and peak stored-sample memory on fixed cases. Investigate
  regressions above an agreed threshold; provisionally 10% after repeated
  measurements. Do not sacrifice reference correctness for a timing target.
- **API quality:** explicit exports, typed public signatures, documented
  extension points, no unintended camelCase APIs/legacy spellings, no stale
  notebook calls, and accurate NumPy-style docstrings. Preserve user variable
  identifiers and external API spellings when applying naming checks.
- **Delivery:** execute maintained tutorial notebooks in a clean environment,
  build Sphinx with warnings as errors, build wheel/sdist, check metadata, and
  run installed-package examples from outside the repository. Keep network/FE
  integration tutorials in an explicit optional job with stated dependencies.

Retain Black initially and introduce a naming/import linter with a small,
reviewed exception list. Replace formatting-after-merge PRs with checks before
merge. Consolidate duplicate test workflows, retain a deliberate coverage job,
and run both minimum-dependency and current-dependency environments. Test Linux,
Windows, and macOS, with a full version matrix on Linux and representative
versions on the other platforms.

Use the root contributor guide and PR template for v2 contributions. In stage 0,
make formatting checks required on `v2.0`; introduce naming/import enforcement
in stage 2 as the source migrates. Contributor guidance describes the target
conventions now, but does not imply those automated checks already exist.

Proposed Python floor: **3.11**, subject to checking FE integration users and
the actual NumPy/SciPy support matrix in stage 1. Carry #96's SciPy requirement
forward and choose tested compatible dependency bounds; do not mistake that
PR's lower bound for a complete 2.0 support policy. Retain current support during
baseline integration. Verify and publish the final supported versions at RC.

## 9. User migration and release policy

Ship one canonical API in 2.0. Do not keep permanent camelCase aliases in the
main namespace. Maintain the final stable pre-2.0 line for critical fixes during
a proposed 12-month transition, with dated documentation and reproducible
installation instructions. The maintainer can adjust that support commitment
before release; it is not a promise already made to users.

Provide a migration guide with before/after examples, an exhaustive symbol and
keyword map, import relocations, options/defaults, coordinate/index semantics,
result/table schemas, subclass hooks, and removed features. Explain that old
pickled solver objects are not portable; offer plain-data export where useful.
Ship a conservative syntax-aware codemod for unambiguous imports/calls/keywords,
with dry-run diffs. Flag getters-to-results, options splitting, shape changes,
and parameter-mode conversions for manual review. Never globally replace
arbitrary user function names, strings, or engineering symbols.

Release progression: internal integrated baseline → `2.0.0a1` after the core
API works → public beta with all capabilities and migration guide → RC with
API freeze → `2.0.0`. Give a small group of users representative calibration,
assessment, and external-solver scripts to exercise during beta. After API
freeze, defer elective restructuring and new algorithms to later releases.

Serve stable and 2.0 development documentation separately. Update versioning,
package metadata (including the README content type), badges, Python
classifiers, and changelog together at release preparation. Ensure development
branch workflows build artifacts without publishing stable documentation or
PyPI releases. The final `v2.0` → `main` integration and release publication are
distinct from developing and testing the migration.

## 10. Decisions to settle in the first implementation review
