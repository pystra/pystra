# PySTRA 2.0.0a1 (alpha) — draft release note

> Draft for the GitHub release and PyPI description of the first 2.0 alpha.
> Not yet published. See "Before publishing" at the end.

PySTRA 2.0.0a1 is the first alpha of PySTRA 2.0, a new major version with a
breaking API. It is for trying out 2.0 and reporting problems, not for
production work.

```
python -m pip install --pre "pystra==2.0.0a1"
```

1.x remains available: `python -m pip install "pystra<2"`.

## What's in 2.0

- **One consistent interface.** Analyses take `(model, limit_state, *, options=...)`
  and return immutable result records; settings are validated options objects;
  simulations take `rng`; errors are `ModelError` and `AnalysisError`.
- **More methods.** Active learning (Kriging, sparse PCE, PC-Kriging), system
  reliability, explicit copulas and joint distributions, and the Strong Maximum Test.
- **Engineering workflows.** Code calibration with normalized reliability, load
  combinations, and design-decision and target-reliability studies.
- **Accurate at high reliability.** Tail-accurate transformations and log-space
  estimators keep results finite at very large reliability indices.
- **Corrections.** Several 1.x results change where 2.0 fixes a numerical error,
  including SORM curvatures and every result that uses `GEVmin` (now `GEVMin`).

See the What's New page (`docs/source/whatsnew.rst`), the migration guide
(`docs/source/migrating.rst`) with its complete symbol map, and the changelog.

## Upgrading

2.0 has no aliases for renamed names (apart from `GEVmax`); old names raise errors
that name their replacements. Follow the checklist at the top of the migration
guide. There is not yet an automatic converter for user scripts.

## Known limitations of this alpha

- The public contracts for batched evaluators and for extending distributions
  can still change before the beta.
- Tested on Linux with Python 3.12 and 3.13; Windows, macOS and minimum-dependency
  testing are still to come.
- Details of the API can change before the release candidate.

## Feedback

Please report problems, and especially scripts that are hard to migrate, as
GitHub issues.

## Before publishing (maintainer checklist, remove from the published note)

From §7 and §9 of `docs/v2.0-migration-plan.md` and the 12 September review:

1. Classifier: `Development Status :: 4 - Beta` in `pyproject.toml` should be
   `3 - Alpha` for this release.
2. `.github/workflows/publish.yml` publishes to production PyPI on any manual
   dispatch and does not depend on the test workflow; restrict it to the release
   tag, require the tests, and use trusted publishing.
3. Documentation: 2.0 pages are not published yet; publish them separately from
   the stable 1.x documentation before linking to them from the release.
4. Changelog: add a `2.0.0a1` heading, or keep `2.0.0 (unreleased)` and point
   to it.
5. README: its installation section tells users to install from the branch;
   add the `--pre` install once published.
6. Tag `v2.0.0a1` on the release commit after the full gates pass there.
